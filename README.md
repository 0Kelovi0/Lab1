# Паралельне обчислення суми елементів масиву (Java та C#)

## Структура

```
parallel-sum/
├── java/ArraySumBenchmark.java       # 7 реалізацій (Java 21)
└── csharp/
    ├── Program.cs                    # 6 реалізацій (.NET 8)

```

## Загальний підхід

Масив розбивається на `parts` неперетинних діапазонів
`[from, to)`. Кожен потік/задача обчислює **часткову суму** свого діапазону
в `long`-акумулятор (щоб уникнути переповнення `int`). Після завершення всіх
потоків відбувається **синхронне** об'єднання часткових сум (`join`,
`Future.get`, `Task.Wait`, `Interlocked.Add` тощо) — це і є критична секція
алгоритму, її вартість мінімальна (O(parts)), тому вона не впливає суттєво
на загальний час.

Запуск:


**це очікуваний результат для 1 ядра, а не помилка реалізацій**.

## Очікувана поведінка на реальній багатоядерній машині

Для суми елементів масиву задача є **пам'яті-обмеженою** (memory-bound):
кожен елемент читається й додається один раз — O(1) обчислень на елемент.
Тому:

1. **Прискорення обмежене пропускною здатністю пам'яті (RAM bandwidth)**,
   а не кількістю ядер CPU: на 4–8 ядрах типове реальне прискорення для
   такої задачі становить **~2–4x**, а не лінійне 4x–8x, бо всі потоки
   конкурують за одну шину пам'яті.
2. Оптимальна кількість частин (`parts`) ≈ кількість фізичних ядер.
   Збільшення `parts` понад це не дає виграшу, а лише збільшує накладні
   витрати на створення потоків/задач і об'єднання результатів.
3. На **малих** масивах (десятки-сотні тисяч елементів) багатопотокові
   реалізації **програють** однопотоковій — вартість створення потоків
   і синхронізації перевищує виграш від паралелізму. Виграш з'являється
   лише на великих обсягах даних (тому в умові й вимагається ≥10⁹
   елементів).

## Порівняльний висновок по реалізаціях (Java)

Впорядковано за очікуваною ефективністю на багатоядерній машині
(від найкращої до найгіршої) для задачі "сума масиву":

1. **ForkJoinPool / Parallel Stream** — найефективніші для CPU-bound
   рекурсивного розбиття: `ForkJoinPool` використовує work-stealing,
   балансуючи навантаження між потоками автоматично; `Parallel Stream`
   під капотом використовує той самий `ForkJoinPool.commonPool()`, тому
   має практично ідентичну продуктивність, але простіший у написанні
   (декларативний стиль). Мінімальні накладні витрати на диспетчеризацію.
2. **ExecutorService + Future** — близька продуктивність до Fork/Join,
   але без work-stealing: якщо частини нерівномірні за обчислювальним
   навантаженням (тут — рівні), можливий дисбаланс. Для суми масиву з
   рівними діапазонами — практично однакова швидкість.
3. **Manual Thread** — найбільші накладні витрати: створення нативного
   `Thread` для кожного виклику дорожче, ніж перевикористання потоків із
   пулу. При невеликій кількості частин різниця несуттєва, але цей підхід
   не масштабується (немає пулу — при частому виклику суму варто рахувати
   через пул потоків).
4. **CompletableFuture** — накладні витрати зіставні з `ExecutorService`
   (фактично працює поверх пулу потоків), додає невелику вартість на
   побудову ланцюжка `allOf/join`.
5. **Virtual Threads** — для цієї **CPU-bound** задачі не дають переваги
   над платформними потоками (і на малих масивах вимірювання показують
   гірший або порівнянний результат): віртуальні потоки оптимізовані для
   задач, обмежених вводом-виводом (I/O-bound) — велика кількість потоків,
   що часто блокуються на I/O. Обчислення суми масиву — чисто CPU-bound,
   тому виграшу від "дешевих" потоків Loom тут немає; кількість
   одночасно виконуваних потоків все одно обмежена кількістю ядер (carrier
   threads).

## Порівняльний висновок по реалізаціях (C#)

1. **Partitioner.Create + Parallel.ForEach** — очікувано найефективніший:
   явне range-партиціювання зменшує кількість callback-викликів (кожен
   потік обробляє цілий діапазон, а не елемент за елементом), а
   `Interlocked.Add` дешевший за `lock`.
2. **Parallel.For з локальним акумулятором** — практично та ж ефективність:
   `localInit/localFinally` запобігає false sharing і зайвій синхронізації
   на кожній ітерації, об'єднання відбувається один раз на потік.
3. **PLINQ** — трохи повільніший за `Parallel.For`/`Partitioner` через
   додаткові накладні витрати LINQ-конвеєра (буферизація, злиття
   результатів), але значно простіший код (`.AsParallel().Sum()`).
4. **Task.Run + WhenAll** — порівнянний з `Parallel.For`, якщо кількість
   задач = кількості ядер; TPL використовує той самий `ThreadPool`.
5. **Manual Thread** — як і в Java, найбільші накладні витрати через
   створення нативних потоків ОС замість перевикористання пулу.

## Загальний підсумок

- Паралелізація **дає реальний виграш лише на великих масивах** (≥10⁸–10⁹
  елементів) і **на машинах із декількома фізичними ядрами**; на
  однойядерній системі або для малих масивів однопотокова реалізація
  залишається найшвидшою через відсутність накладних витрат на потоки.
- Задача обчислення суми — **memory-bound**, тому максимальне прискорення
  обмежується пропускною здатністю пам'яті, а не кількістю потоків:
  практичний оптимум `parts` ≈ кількість фізичних ядер.
- Серед "просунутих" засобів (`ForkJoinPool`/`Parallel Stream` у Java,
  `Partitioner`/`Parallel.For` у C#) продуктивність вища за "базові"
  засоби (голі `Thread`) завдяки перевикористанню пулу потоків та
  балансуванню навантаження, при цьому код лишається компактнішим.
- `Virtual Threads` (Java) — приклад засобу, що **не підходить** для
  CPU-bound задач: його перевага розкривається лише на I/O-bound
  навантаженні з тисячами одночасних потоків.
